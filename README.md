# АИ ООС Demo

Репозиторий подготовлен как рабочая основа для demo-стенда АИ ООС — системы поддержки инспекционного контроля в области охраны окружающей среды.

## Назначение

Проект ориентирован на демонстрацию сценариев работы с материалами экологического контроля:

- график проверок;
- чек-листы и исторические чек-листы;
- база знаний с федеральными, региональными и корпоративными требованиями;
- шаблоны чек-листов;
- карточки объектов проверки;
- реестр нарушений и материалы по результатам проверок;
- справочники для наполнения интерфейса и бизнес-логики.

## Исходные материалы

В локальной папке проекта находятся демонстрационные документы и справочные данные:

- `Сценарий демо-показа АИ ООС.docx` — сценарий демонстрации;
- `Техническое задание и план работ для Demo-стенда АИ ООС.pdf` — техническое задание и план работ;
- `ФТ АИ ОСС.docx` — функциональные требования;
- `01_📅 График проверок/` — программа и визуальные материалы графика проверок;
- `02_📂 Чек-листы/` — исторические чек-листы;
- `03_📚 База знаний/` — реестры требований и нормативные документы;
- `04_📄 Шаблоны чек-листов/` — формы чек-листов;
- `06_🏭 Объекты/` — карточки объектов и экраны реестра объектов аудита;
- `07_⚠️ Реестр нарушений/` — отчеты, акты, реестры несоответствий и предложения по результатам контроля;
- `08_📋 Справочники/` — справочники предметной области;
- `Дулаева - рабочие материалы/` — рабочие материалы по наполнению и сценариям.

Эти файлы добавлены в `.gitignore`, потому что являются объемными бинарными и справочными материалами. В Git предполагается хранить исходный код, конфигурацию проекта и документацию по разработке.

## Быстрый старт

Проверить установленный SDK:

```bash
dotnet --info
```

Восстановить зависимости и собрать проект:

```bash
dotnet restore OssDemo.slnx
dotnet build OssDemo.slnx
```

Запустить web-приложение:

```bash
dotnet run --project src/OssDemo.Web/OssDemo.Web.csproj
```

После запуска приложение будет доступно по адресам, которые выведет команда `dotnet run`.

## Дальнейшая разработка

Рекомендуемый порядок работ:

1. Описать ключевые сущности предметной области: проверки, объекты, чек-листы, требования, нарушения, справочники.
2. Подготовить модель данных и слой доступа к данным.
3. Реализовать основные Razor Pages для просмотра и редактирования справочников.
4. Добавить сценарий формирования индивидуального чек-листа.
5. Подключить импорт демонстрационных Excel/PDF/DOCX-материалов отдельным управляемым процессом, не храня исходные бинарные файлы в Git.

## Тестовый ИИ-консультант

В интерфейсе подключён тестовый чат с Amvera LLM Inference. Сервер вызывает
OpenAI-совместимый endpoint `POST https://inference.waw0.amvera.ru/v1/chat/completions`
с моделью `qwen3_30b`. Токен остаётся на сервере: браузер его не получает.

### Настройка в Amvera

Автодеплой по push и секреты настраиваются независимо: Amvera берёт код из Git,
а реальные ключи, токены и пароли хранятся в проекте, вне репозитория. В Git
добавлен [`.env`](.env) только с несекретными настройками embedding-сервиса;
Amvera подхватывает его при запуске контейнера. Файл `amvera.yaml` не поддерживает
безопасные ссылки на секреты. Шаблон полного локального набора имён находится в
[`.env.example`](.env.example), но не содержит рабочих значений.

В проекте `ossDemo` откройте «Переменные и секреты» и создайте:

| Имя | Тип | Значение |
| --- | --- | --- |
| `AI__ApiToken` | секрет | токен Amvera LLM для Qwen3-30B |
| `Embeddings__ApiKey` | секрет | то же значение, что `EMBEDDINGS_API_KEY` в `minilm` |
| `Docling__ApiKey` | секрет | ключ API сервиса Docling |
| `ConnectionStrings__OssDatabase` | секрет | внутренняя строка подключения к PostgreSQL |
| `Embeddings__BaseUrl` | не требуется | уже передаётся из отслеживаемого `.env` |
| `Embeddings__Model` | не требуется | уже передаётся из отслеживаемого `.env` |
| `Docling__BaseUrl` | не требуется | уже передаётся из отслеживаемого `.env` |

После изменения значений перезапустите или передеплойте приложение. Amvera не
предоставляет переменные на этапе сборки Docker, они доступны только запущенному
контейнеру. Двойное подчёркивание обязательно: .NET преобразует, например,
`AI__ApiToken` в настройку `AI:ApiToken`.

### Локальный запуск

В `cmd.exe` перед запуском приложения временно задайте переменную окружения:

```bat
set AI__ApiToken=ваш_токен
dotnet run --project src/OssDemo.Web/OssDemo.Web.csproj
```

Переменная действует только в текущем окне терминала. На этом этапе чат является
только проверкой модели: поиск по базе знаний и цитирование документов будут
добавлены в RAG-этапе.

## Embedding-сервис для RAG

Отдельный сервис с ONNX-моделью находится в репозитории
`https://git.msk0.amvera.ru/aleksandr12224411/minilm`. Перед подключением
`ossDemo` он должен быть успешно развёрнут в Amvera и иметь секрет
`EMBEDDINGS_API_KEY`.

В переменных и секретах приложения `ossDemo` задайте:

```text
Embeddings__BaseUrl=http://amvera-aleksandr12224411-run-minilm/  # переменная
Embeddings__ApiKey=<то же значение, что EMBEDDINGS_API_KEY в minilm>  # секрет
Embeddings__Model=sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2  # переменная
```

Внутренний адрес используется только между приложениями Amvera; не добавляйте
ему публичный домен и не передавайте ключ браузеру. Имя внутреннего хоста
построено по документированному шаблону Amvera для приложения `minilm`.

После деплоя `ossDemo` проверьте связь, войдя в demo и выполнив запрос:

```text
POST /api/rag/embedding-check
```

Успешный ответ имеет вид `{"ready":true,"model":"...","dimensions":384}`.
Endpoint проверяет авторизацию, имя модели, размерность и корректность чисел,
но не возвращает вектор. `GET /api/rag/status` показывает только статус
конфигурации, без адреса и ключа.

При наличии `ConnectionStrings__OssDatabase` приложение само включает
расширение `pgvector`, создаёт таблицы, HNSW-индекс и FTS-индекс, а затем индексирует
подготовленные demo-источники. После этого `/api/ai/chat` объединяет полнотекстовые
и векторные кандидаты методом reciprocal rank fusion (RRF). Для русского текста FTS
использует встроенную конфигурацию PostgreSQL `simple`: она не зависит от наличия
словаря на хосте и корректно индексирует кириллицу. Реквизиты документа (тип, номер,
орган, дата) выделяются при импорте и при единственном точном совпадении ограничивают
контекст только этим документом; при нескольких совпадениях чат просит уточнение.

Reranker по умолчанию отключён. Если появится подтверждённый внутренний совместимый
endpoint, задайте `Rag__Reranker__Endpoint`; он получает батч кандидатов и при любой
ошибке поиск без задержки деградирует к RRF.

Для Amvera используйте внутреннюю строку подключения:

```text
ConnectionStrings__OssDatabase=Host=amvera-aleksandr12224411-cnpg-oss-rw;Port=5432;Database=OSSDB;Username=aleksandr12224411;Password=<пароль БД>;SSL Mode=Disable
```

Внешний домен БД не нужен приложению и не должен использоваться в production.

### Импорт документов

Подготовленные Folio-OCR TXT из `knowledge-inbox/` поставляются с приложением и
индексируются при каждом запуске без повторного OCR и Docling. Неизменённые файлы
повторно не обрабатываются: проверяются имя и SHA-256.

В `amvera.yaml` приложения `ossDemo` также подключён persistent volume в `/data`.
Дополнительные PDF, DOCX, XLSX или TXT можно поместить в `/data/inbox` и перезапустить
приложение. Офисные документы преобразуются через Docling, TXT читаются напрямую;
после этого текст и метаданные сохраняются в PostgreSQL, а для RAG создаются векторные
фрагменты.

Для импорта добавьте `Docling__ApiKey` в секреты Amvera. Ключ используется только
сервером `ossDemo` при вызове Docling.
