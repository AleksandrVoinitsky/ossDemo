# АИ ООС Demo

Репозиторий подготовлен как рабочая основа для demo-стенда АИ ООС — системы поддержки инспекционного контроля в области охраны окружающей среды.

## Назначение

Проект ориентирован на демонстрацию сценариев работы с материалами экологического контроля:

- график проверок;
- чек-листы и исторические чек-листы;
- база знаний с федеральными, региональными и корпоративными требованиями;
- шаблоны чек-листов;
- карточки объектов проверки;
- реестр нарушений и материалы по результатам проверок;
- справочники для наполнения интерфейса и бизнес-логики.

## Исходные материалы

В локальной папке проекта находятся демонстрационные документы и справочные данные:

- `Сценарий демо-показа АИ ООС.docx` — сценарий демонстрации;
- `Техническое задание и план работ для Demo-стенда АИ ООС.pdf` — техническое задание и план работ;
- `ФТ АИ ОСС.docx` — функциональные требования;
- `01_📅 График проверок/` — программа и визуальные материалы графика проверок;
- `02_📂 Чек-листы/` — исторические чек-листы;
- `03_📚 База знаний/` — реестры требований и нормативные документы;
- `04_📄 Шаблоны чек-листов/` — формы чек-листов;
- `06_🏭 Объекты/` — карточки объектов и экраны реестра объектов аудита;
- `07_⚠️ Реестр нарушений/` — отчеты, акты, реестры несоответствий и предложения по результатам контроля;
- `08_📋 Справочники/` — справочники предметной области;
- `Дулаева - рабочие материалы/` — рабочие материалы по наполнению и сценариям.

Эти файлы добавлены в `.gitignore`, потому что являются объемными бинарными и справочными материалами. В Git предполагается хранить исходный код, конфигурацию проекта и документацию по разработке.

## Быстрый старт

Проверить установленный SDK:

```bash
dotnet --info
```

Восстановить зависимости и собрать проект:

```bash
dotnet restore OssDemo.slnx
dotnet build OssDemo.slnx
```

Запустить web-приложение:

```bash
dotnet run --project src/OssDemo.Web/OssDemo.Web.csproj
```

После запуска приложение будет доступно по адресам, которые выведет команда `dotnet run`.

## Дальнейшая разработка

Рекомендуемый порядок работ:

1. Описать ключевые сущности предметной области: проверки, объекты, чек-листы, требования, нарушения, справочники.
2. Подготовить модель данных и слой доступа к данным.
3. Реализовать основные Razor Pages для просмотра и редактирования справочников.
4. Добавить сценарий формирования индивидуального чек-листа.
5. Подключить импорт демонстрационных Excel/PDF/DOCX-материалов отдельным управляемым процессом, не храня исходные бинарные файлы в Git.

## Тестовый ИИ-консультант

В интерфейсе подключён RAGify 3.0.0. Он выполняет загрузку документов,
Markdown-ориентированную нарезку, векторизацию встроенной ONNX-моделью
`paraphrase-multilingual-MiniLM-L12-v2/model_O1.onnx`, хранение и поиск в
PostgreSQL с расширением `pgvector`, а также локальный BM25 reranker.

Для генерации ответа RAGify использует OpenAI-совместимый endpoint Amvera с
моделью `qwen3_30b`. Токен остаётся на сервере: браузер его не получает.

### Настройка в Amvera

Автодеплой по push и секреты настраиваются независимо: Amvera берёт код из Git,
а реальные ключи, токены и пароли хранятся в проекте, вне репозитория. Amvera
подхватывает [`.env`](.env) при запуске контейнера. Файл `amvera.yaml` не поддерживает
безопасные ссылки на секреты. Шаблон полного локального набора имён находится в
[`.env.example`](.env.example), но не содержит рабочих значений.

ONNX-модель не хранится в Git и не включается в Docker-образ из-за размера. При
первом запуске контейнер скачивает зафиксированную ревизию
`paraphrase-multilingual-MiniLM-L12-v2` в persistent volume `/data/ragify-model`,
проверяет SHA-256 обоих файлов и использует их локально. На последующих запусках
корректные файлы из volume повторно не скачиваются.

В проекте `ossDemo` откройте «Переменные и секреты» и создайте:

| Имя | Тип | Значение |
| --- | --- | --- |
| `AI__ApiToken` | секрет | токен Amvera LLM для Qwen3-30B |
| `ConnectionStrings__OssDatabase` | секрет | внутренняя строка подключения к PostgreSQL |

После изменения значений перезапустите или передеплойте приложение. Amvera не
предоставляет переменные на этапе сборки Docker, они доступны только запущенному
контейнеру. Двойное подчёркивание обязательно: .NET преобразует, например,
`AI__ApiToken` в настройку `AI:ApiToken`.

### Локальный запуск

В `cmd.exe` перед запуском приложения временно задайте переменную окружения:

```bat
set AI__ApiToken=ваш_токен
dotnet run --project src/OssDemo.Web/OssDemo.Web.csproj
```

После деплоя `ossDemo` проверьте встроенную ONNX-модель, войдя в demo и выполнив запрос:

```text
POST /api/rag/embedding-check
```

Успешный ответ содержит `{"ready":true,"model":"...model_O1.onnx","dimensions":384}`.
Endpoint не обращается к внешнему embedding-сервису. `GET /api/rag/status`
показывает статус RAGify и число векторов в pgvector.

При наличии `ConnectionStrings__OssDatabase` приложение само включает
расширение `pgvector`, создаёт таблицу `ragify_vectors` и векторный индекс, а затем
индексирует подготовленные demo-источники через RAGify. `/api/ai/chat` вызывает
`RAGify.AnswerAsync`: фреймворк ищет релевантные фрагменты, применяет встроенный BM25
reranker и передаёт только найденный контекст генератору ответа.

Для Amvera используйте внутреннюю строку подключения:

```text
ConnectionStrings__OssDatabase=Host=amvera-aleksandr12224411-cnpg-oss-rw;Port=5432;Database=OSSDB;Username=aleksandr12224411;Password=<пароль БД>;SSL Mode=Disable
```

Внешний домен БД не нужен приложению и не должен использоваться в production.

### Импорт документов

Подготовленные документы из `knowledge-inbox/` поставляются с приложением и
индексируются при каждом запуске RAGify. Неизменённые файлы повторно не обрабатываются:
проверяются имя и SHA-256.

В `amvera.yaml` приложения `ossDemo` также подключён persistent volume в `/data`.
Дополнительные PDF, DOCX, XLSX, HTML, Markdown, CSV, JSON или TXT можно поместить в
`/data/inbox` и перезапустить приложение. RAGify извлекает текст, сохраняет векторы
в PostgreSQL и использует их для RAG-поиска.
