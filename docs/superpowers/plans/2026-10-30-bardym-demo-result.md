# Персонализация результата демонстрации Бардымского ЛПУМГ

**Цель:** на последнем шаге формирования показать пункты заказчика из Excel и скачивать тот же исходный XLSX существующей кнопкой.

**Основание:** запрос пользователя от 30.10.2026. Предыдущая спецификация универсального экспорта трёх форматов не входит в эту доработку.

**Источник:** `D:/OCC/Бардымское_ЛПУ_Чек_лист_ИК_ООС_2024г_на_последний_шаг.xlsx`, лист `Экология экспл`, 211 нумерованных пунктов. Целевой существующий чек-лист: `ed3a2f07-8bd3-4408-90f5-88a9851deb6a`.

## Ограничения

- Сохранить текущую страницу результата, стили и кнопки. Не добавлять подписи, пояснения, подсказки или настройки в интерфейс.
- Не изменять PDF, Word, прочие объекты и этапы формирования.
- Итоговый набор пунктов равен Excel: без дополнительных сгенерированных пунктов и дублей.
- Скачать исходные байты XLSX, а не пересозданную книгу.
- Применять персонализацию к указанному результату и новым результатам демонстрационного формирования Бардымского ЛПУМГ. Идентифицировать объект по стабильному ID, полученному из справочника, а не по частичному совпадению названия.

## План реализации

### 1. Подготовить исходный файл и проверяемый набор пунктов

- [ ] Создать отдельную ветку разработки.
- [ ] Поместить неизменённый XLSX в `data/seed/demo/`, подключить его как embedded resource в `src/OssDemo.Web/OssDemo.Web.csproj`, чтобы файл гарантированно попал в публикацию.
- [ ] Добавить воспроизводимое извлечение шести колонок Excel в `scripts/` и сохранить нормализованные данные рядом с XLSX. Учитывать shared strings, пустые ячейки, объединённые строки разделов и нумерацию внутри разделов.
- [ ] Проверить 211 пунктов, порядок, разделы, основания и отсутствие потери текста. Не переносить реквизиты шапки в список пунктов.

### 2. Подставить пункты в результат демонстрационного формирования

- [ ] Добавить изолированный провайдер `BardymDemoChecklist` в `src/OssDemo.Web/Checklists/`: источник пунктов, проверка применимости и доступ к исходному XLSX.
- [ ] В точке сохранения итогового демонстрационного результата использовать набор из Excel вместо сформированного набора; исследовать и выбрать фактически используемый путь `CreateAiDraftAsync`/`CreateDraftAsync`, не менять оба без необходимости.
- [ ] Сохранять пункты в БД с устойчивыми идентификаторами и последовательными позициями. Повторное открытие или повтор запроса не должно добавлять пункты заново.
- [ ] Подготовить адресное идемпотентное обновление указанного существующего чек-листа: замена только его пунктов в транзакции, предварительное сохранение исходных значений для восстановления. Не менять общие шаблоны или историю остальных чек-листов.
- [ ] Не выдавать фиктивные новые источники или текстовые пометки для пунктов. Использовать существующий вид карточек результата.

### 3. Скачать исходный Excel

- [ ] В `ChecklistApi.cs` в ветке `xlsx` для целевого демонстрационного результата возвращать embedded XLSX с исходным именем файла и корректным MIME-типом.
- [ ] Сохранить существующий URL `/exports/checklists/{id}.xlsx` и элемент `[data-export-xlsx]`. Не привязывать поведение ко всем элементам с общим классом `btn btn-outline-primary`.
- [ ] Для остальных чек-листов оставить текущий экспорт.

### 4. Проверить и передать результат

- [ ] Добавить проверки в `tests/OssDemo.Checklists.Tests/BardymDemoChecklistChecks.cs` и вызвать из `Program.cs`: 211 пунктов, точное сопоставление полей Excel, порядок разделов, отсутствие дублей при повторном формировании, изоляция другого объекта.
- [ ] Сравнить SHA-256 скачанного тела с исходным XLSX: должны совпадать. Проверить имя файла и MIME-тип.
- [ ] Выполнить restore, Release build и тесты чек-листов по AGENTS.md. Выполнить publish и проверить наличие embedded XLSX в собранном приложении.
- [ ] На локальном стенде пройти формирование Бардымского ЛПУМГ, повторно открыть результат и скачать Excel. Проверить, что интерфейс не приобрёл новых элементов и остальные форматы используют прежние обработчики.
- [ ] Проверить diff на отсутствие посторонних изменений. Публикация и адресное обновление данных хостинга выполняются отдельным согласованным действием после локальной проверки.

## Известное ограничение проверки

Удалённая страница результата недоступна через инструмент просмотра. Перед изменением существующей записи необходимо проверить её объект, статус и текущие данные через разрешённый доступ к приложению или БД. Исходный файл локально доступен.

## Результат реализации

Реализация выполнена в ветке `feat/bardym-demo-result`. Вместо отдельного скрипта и JSON используется прямое чтение встроенного исходного XLSX: это единый источник пунктов и скачивания. SQL привязывает новый результат к записи объекта через facility_id и проверяет точное название и оба используемых в проекте slug. Для персонализированных результатов сохраняется внутренний признак, не выводимый в JSON интерфейса. Общие шаблоны и прочие существующие результаты не меняются.

Проверено на отдельном контейнере PostgreSQL: оба пути создания, все поля 211 пунктов, устойчивость ID при открытии, адресная миграция и её повтор, резервная копия, прежний экспорт другого объекта. Через HTTP проверены результат API и побайтовое совпадение скачанного XLSX, имя файла и MIME. Release build и publish успешны; встроенный файл в опубликованной сборке имеет исходную SHA-256. Проверка RAG останавливается на ранее отсутствующей ONNX-модели; код RAG не менялся.

На хостинг изменения не отправлялись. Полный визуальный проход мастера в браузере не выполнялся; представление и JavaScript страницы не изменены. Адресное обновление записи хостинга выполнится после согласованной публикации при запуске приложения, только при совпадении объекта и с резервной копией исходных пунктов в БД.
