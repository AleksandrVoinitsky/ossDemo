# Шаблоны и история чек-листов — дизайн

## Цель

Перевести шаблоны и исторические чек-листы из CSV и локальных JSON-файлов в PostgreSQL, разделить их в интерфейсе и добавить полноценный редактор быстрых шаблонов. Рабочий чек-лист создаётся как снимок шаблона, остаётся редактируемым до утверждения и попадает в историю только после утверждения.

## Термины и правила

- **Шаблон** — редактируемая заготовка чек-листа для выбранного объекта проверки. Шаблон можно создать, открыть, изменить, скопировать и удалить.
- **Черновик** — рабочий чек-лист, созданный из шаблона. Его пункты являются независимым снимком шаблона.
- **Исторический чек-лист** — утверждённый чек-лист. Его нельзя изменять, удалять или возвращать в черновики; он доступен для просмотра и экспорта.
- Изменение или удаление шаблона не влияет на созданные ранее черновики и исторические записи.
- Исторические CSV-наборы импортируются как уже утверждённые чек-листы. Шаблонные CSV-наборы импортируются как обычные редактируемые шаблоны.
- После переноса приложение не читает CSV и не использует файловое хранилище рабочих чек-листов.

## Структура данных

Инициализация следует принятому в проекте подходу: сервис на `Npgsql` выполняет идемпотентный DDL и начальное заполнение в транзакции.

### `app_checklist_templates`

- `id UUID PRIMARY KEY`
- `name TEXT NOT NULL`
- `facility_id UUID NOT NULL REFERENCES app_facilities(id)`
- `version BIGINT NOT NULL DEFAULT 1`
- `created_at TIMESTAMPTZ NOT NULL`
- `updated_at TIMESTAMPTZ NOT NULL`

`version` используется для оптимистической блокировки редактора. Удаление шаблона физическое и разрешено независимо от наличия созданных по нему чек-листов.

### `app_checklist_template_sections`

- `id UUID PRIMARY KEY`
- `template_id UUID NOT NULL REFERENCES app_checklist_templates(id) ON DELETE CASCADE`
- `title TEXT NOT NULL`
- `position INTEGER NOT NULL`

### `app_checklist_template_items`

- `id UUID PRIMARY KEY`
- `section_id UUID NOT NULL REFERENCES app_checklist_template_sections(id) ON DELETE CASCADE`
- `position INTEGER NOT NULL`
- `title TEXT NOT NULL`
- `basis TEXT NOT NULL`
- `note TEXT NOT NULL DEFAULT ''`

Позиции разделов и пунктов непрерывны и начинаются с 1. Уникальные ограничения на сочетание родительского идентификатора и позиции предотвращают неоднозначный порядок.

### `app_checklists`

- `id UUID PRIMARY KEY`
- `name TEXT NOT NULL`
- `facility_id UUID NULL REFERENCES app_facilities(id) ON DELETE SET NULL`
- `facility_name TEXT NOT NULL`
- `template_id UUID NULL REFERENCES app_checklist_templates(id) ON DELETE SET NULL`
- `template_name TEXT NOT NULL`
- `inspection_started_on DATE NULL`
- `inspection_finished_on DATE NULL`
- `status TEXT NOT NULL CHECK (status IN ('draft', 'approved'))`
- `created_at TIMESTAMPTZ NOT NULL`
- `updated_at TIMESTAMPTZ NOT NULL`
- `approved_at TIMESTAMPTZ NULL`
- `approved_by TEXT NULL`
- `legacy_source_key TEXT NULL UNIQUE`

Названия объекта и шаблона сохраняются снимками. Поэтому история остаётся читаемой после переименования или удаления исходных сущностей. `legacy_source_key` обеспечивает повторяемый безопасный импорт исходных исторических данных.

### `app_checklist_items`

- `id UUID PRIMARY KEY`
- `checklist_id UUID NOT NULL REFERENCES app_checklists(id) ON DELETE CASCADE`
- `position INTEGER NOT NULL`
- `section TEXT NOT NULL`
- `title TEXT NOT NULL`
- `basis TEXT NOT NULL`
- `result TEXT NOT NULL DEFAULT ''`
- `nonconformity TEXT NOT NULL DEFAULT ''`
- `note TEXT NOT NULL DEFAULT ''`
- `origin TEXT NOT NULL`

Исторические записи не удаляются через пользовательский API. Каскадное удаление пунктов действует только при административном удалении самой записи из базы.

### `app_data_migrations`

- `key TEXT PRIMARY KEY`
- `applied_at TIMESTAMPTZ NOT NULL`

Ключ начального переноса фиксирует успешную загрузку старых данных и исключает повторный импорт.

## Перенос исходных данных

Текущие шесть CSV-файлов преобразуются во время разработки в типизированные начальные данные C#. В приложение не переносится общий CSV-парсер и не остаётся runtime-зависимости от CSV.

При первом обращении к сервису чек-листов инициализатор:

1. создаёт таблицы и индексы;
2. обеспечивает наличие объектов, встречающихся в исходных наборах;
3. в одной транзакции проверяет ключ миграции;
4. добавляет три редактируемых шаблона со всеми разделами и пунктами;
5. добавляет три исторических чек-листа со статусом `approved`, исходными периодами, результатами, несоответствиями и примечаниями;
6. записывает ключ миграции и фиксирует транзакцию.

Стабильные идентификаторы и `ON CONFLICT` защищают от дублей при повторном запуске. После реализации удаляются `Data/Checklists/catalog.json`, исходные CSV и настройки их копирования при публикации.

## Серверные компоненты и API

Файловый `ChecklistService` заменяется PostgreSQL-реализацией с небольшими моделями запросов и ответов. Все составные операции используют транзакции.

### Шаблоны

- `GET /api/checklist-templates` — список шаблонов с объектом, количеством разделов и пунктов.
- `GET /api/checklist-templates/{id}` — полный шаблон для просмотра или редактирования.
- `POST /api/checklist-templates` — создание шаблона.
- `PUT /api/checklist-templates/{id}` — полная замена метаданных, разделов и пунктов при совпадении версии.
- `POST /api/checklist-templates/{id}/copy` — копирование под новым именем.
- `DELETE /api/checklist-templates/{id}` — физическое удаление шаблона.

Название, объект, хотя бы один раздел и хотя бы один корректный пункт обязательны. Пустые строки обрезаются. При несовпадении версии API возвращает `409 Conflict` с понятным сообщением о необходимости обновить страницу.

### Рабочие и исторические чек-листы

- `GET /api/checklists/drafts` — список незавершённых черновиков.
- `GET /api/checklists/history` — список только утверждённых записей с фильтрами по строке поиска, объекту и периоду.
- `POST /api/checklists` — создание черновика как снимка выбранного шаблона.
- `GET /api/checklists/{id}` — получение черновика или истории.
- существующая операция добавления пункта сохраняется только для черновика;
- `POST /api/checklists/{id}/approve` — атомарное утверждение.
- `GET /exports/checklists/{id}.xlsx`, `.docx` и `.pdf` — формирование существующих форматов экспорта из сохранённого снимка конкретного чек-листа.

Все изменяющие операции проверяют статус. После утверждения сервер отклоняет изменение пунктов и повторное утверждение. В текущей однопользовательской модели `approved_by` записывается как имя единственной учётной записи `inspector`, а не принимается от клиента.

## Пользовательский интерфейс

### Навигация

Текущая область «Архив и шаблоны» становится страницей с двумя явными вкладками:

- **Шаблоны** — управление быстрыми заготовками;
- **История** — утверждённые чек-листы только для чтения.

Ссылки из мастера формирования и результата ведут в соответствующую вкладку. На странице формирования появляется блок «Незавершённые чек-листы» с возможностью продолжить работу.

### Список шаблонов

Список показывает название, объект, число разделов и пунктов, дату последнего изменения. Доступны поиск и действия «Открыть», «Создать копию» и «Удалить». Удаление требует подтверждения и после успеха не меняет черновики или историю.

### Редактор шаблона

Редактор открывается отдельной страницей и содержит:

- название шаблона;
- выбор объекта из справочника объектов;
- упорядоченный список разделов;
- добавление, переименование, удаление и перемещение разделов;
- добавление, редактирование, удаление и перемещение пунктов;
- поля пункта «Контролируемая позиция», «Основание» и «Примечание»;
- действия «Сохранить» и «Отмена».

Редактор использует обычные кнопки перемещения вверх/вниз, поэтому все операции доступны с клавиатуры и не зависят от drag-and-drop. Ошибки показываются рядом с полями, а введённые данные сохраняются. При конфликте версии пользователь получает сообщение и может открыть актуальную версию в новой загрузке.

### История

Таблица истории показывает название, объект, период проверки, дату утверждения и утвердившего пользователя. Поиск работает по названию и объекту; фильтры — по объекту и датам. Детальная страница использует существующую таблицу пунктов, не показывает элементы редактирования и предоставляет экспорт сохранённой записи в XLSX, DOCX и PDF.

### Утверждение

На странице рабочего чек-листа отображается заметное действие «Утвердить чек-лист». Диалог подтверждения предупреждает, что дальнейшее редактирование невозможно. После успешного утверждения интерфейс открывает запись в истории.

## Ошибки и согласованность

- Все ошибки API имеют единый JSON-ответ с пользовательским сообщением и, для валидации, ошибками отдельных полей.
- `404` означает отсутствие сущности, `400` — ошибку данных, `409` — конфликт версии или состояния.
- Создание и обновление шаблона, создание снимка чек-листа, удаление шаблона и утверждение выполняются в транзакциях.
- Уникальные ограничения и серверная нормализация порядка защищают данные от дубликатов и разрывов позиций.
- Ошибка базы не маскируется файловым fallback: пользователь получает понятное сообщение, а сервер записывает техническую причину в журнал.

## Проверка

Автоматические тесты покрывают:

- проверку обязательных полей шаблона и нормализацию порядка;
- создание, чтение, изменение, копирование и удаление шаблона;
- конфликт версий;
- создание независимого снимка пунктов;
- сохранность черновика и истории после изменения или удаления шаблона;
- запрет изменения утверждённого чек-листа;
- однократный переход `draft -> approved`;
- разделение выдачи черновиков и истории;
- идемпотентность начального переноса данных.

Перед отправкой выполняются тесты, Release-сборка, проверка diff и ручная проверка основных API/UI-сценариев на доступной тестовой конфигурации PostgreSQL.

## Вне текущего объёма

- роли и многоуровневое согласование;
- возврат утверждённого чек-листа в черновик;
- удаление исторических записей через интерфейс;
- импорт новых CSV через интерфейс;
- совместное редактирование в реальном времени;
- изменение визуального оформления XLSX, DOCX и PDF сверх подстановки фактических данных выбранного чек-листа.
