# Дизайн реорганизации репозитория

## Цель

Сделать `ossDemo` предсказуемым рабочим репозиторием: код, тесты, данные, документация, скрипты и локальные артефакты должны иметь отдельные места, а существующие сборка, тесты и Docker-деплой — сохранить поведение.

## Принципы

- Не менять бизнес-логику и публичные HTTP-интерфейсы.
- Не отправлять изменения в удалённый репозиторий: автодеплой не должен запускаться до ручного просмотра.
- Хранить в Git только данные, необходимые для воспроизводимой сборки или инициализации приложения.
- Не хранить секреты в Git; `.env.example` остаётся единственным отслеживаемым env-файлом.
- Не трогать соседние репозитории и модели в `C:\OCC`.

## Целевая структура

```text
ossDemo/
├── .github/                 # CI/CD-конфигурация, если появится
├── data/
│   ├── knowledge-base/      # Markdown, поставляемый с приложением
│   ├── seed/                # Начальные данные приложения в JSON
│   ├── import/              # Подготовленные, но не поставляемые источники
│   └── reference/           # Локальные бинарные и рабочие материалы (ignored)
├── docs/
│   ├── architecture/        # Карта системы и границы компонентов
│   ├── requirements/        # ТЗ и технические требования в Markdown
│   └── superpowers/         # История дизайнов и планов изменений
├── scripts/                 # Обслуживание, миграции и конвертация данных
├── src/                     # Только исходный код приложения и web-ресурсы
├── tests/                   # Исполняемые проверки
├── AGENTS.md                # Правила совместной работы в репозитории
├── README.md                # Входная точка для разработчика
└── deployment files         # Dockerfile, amvera.yaml, solution/config files
```

## Перемещения

- `03_📚 База знаний/` → `data/knowledge-base/`.
- `knowledge-inbox/` → `data/import/knowledge-inbox/`; эти документы остаются отдельным подготовительным набором и не попадают в runtime автоматически.
- `PROJECT_REQUIREMENTS.md` и `RAG_TECHNICAL_SPEC.md` → `docs/requirements/`.
- `tools/convert_historical_checklists.py` → `scripts/convert_historical_checklists.py`.
- Локальные нумерованные каталоги, документы сценария и рабочие материалы → тематические подкаталоги `data/reference/`.
- Сгенерированные `artifacts/`, publish-каталоги, IDE-файлы и worktrees остаются игнорируемыми и не являются частью структуры продукта.

## Отделение кода от начальных данных

`ChecklistSeedData.cs` содержит почти 884 КБ литералов. Его содержимое переносится без смыслового изменения в `data/seed/checklists.json`. Небольшой загрузчик десериализует JSON в существующие record-модели. JSON включается в сборку и публикацию как embedded resource, поэтому загрузка не зависит от текущего каталога процесса и работает одинаково локально и в Docker.

Контракт загрузчика проверяется тестом на корректную десериализацию дат, enum и вложенных коллекций. Существующие проверки количества шаблонов и истории защищают фактический набор от потери при миграции.

## Сборка и деплой

`OssDemo.Web.csproj` меняет только исходные пути данных:

- Markdown из `data/knowledge-base/` по-прежнему публикуется в `knowledge-base/`.
- `data/seed/checklists.json` встраивается в assembly.
- Dockerfile, имя проекта, порт, persistent volume и entrypoint не меняются.

## Документация рабочего процесса

`AGENTS.md` определяет границы каталогов, безопасную работу с секретами, обязательные команды проверки и правило не пушить напрямую ради автодеплоя. `docs/architecture/repository-map.md` объясняет назначение данных и runtime-потоки. README становится короткой актуальной входной точкой и ссылается на подробные требования.

## Проверка

После перемещений выполняются:

1. проверка отсутствия отслеживаемого `.env`;
2. Release-сборка решения;
3. оба консольных набора тестов;
4. `dotnet publish` с проверкой наличия `knowledge-base`;
5. сравнение количества seed-шаблонов и элементов истории с исходным набором;
6. просмотр `git status` и diff на отсутствие случайных файлов.
