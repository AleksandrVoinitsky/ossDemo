# Слой контрольных процедур для персональных чек-листов

## Цель

Формировать для инспектора содержательный персональный чек-лист, сопоставимый с историческим шаблоном на 235 пунктов. Число пунктов не является жёстким лимитом: результат определяется подтверждёнными фактами объекта, применимыми контрольными процедурами и обоснованными нормативными дополнениями.

## Проблема текущей модели

Карточка выбирает крупные критерии классификатора, после чего каждый связанный нормативный фрагмент превращается в самостоятельный пункт. Для Березниковского ЛПУМГ это даёт 2 381 пункт, из которых 2 350 являются механическими копиями требований. Реестр требований обеспечивает нормативную базу, но его строки имеют другую гранулярность и не являются готовыми действиями инспектора.

Исторический шаблон содержит 235 проверенных человеком процедур, однако только 34 из них имеют однозначную автоматическую связь с конкретными строками реестра. Неоднозначность связи с реестром не должна исключать сам утверждённый пункт из рабочего слоя.

## Целевая модель

Между требованиями и итоговым чек-листом вводится сущность `InspectionControl` — контрольная процедура инспектора.

Контрольная процедура содержит:

- стабильный идентификатор и порядок;
- раздел и связанные критерии классификатора;
- проверочный вопрос и нормативное основание из утверждённого шаблона;
- ноль или несколько подтверждённых идентификаторов требований;
- условия применимости к фактам карточки;
- происхождение и статус нормативной связи;
- объяснение включения в конкретный чек-лист.

Статусы нормативной связи: `verified`, `suggested`, `unmapped`. Статус `unmapped` означает, что точная строка реестра ещё не подтверждена; основание из утверждённого шаблона при этом сохраняется и пункт остаётся допустимым для работы.

## Конвейер формирования

1. Карточка предоставляет все известные структурированные факты. Неизвестные значения не блокируют формирование.
2. Классификатор определяет применимые, неприменимые и неопределённые направления контроля.
3. Компоновщик выбирает контрольные процедуры из применимых разделов и уточняет их по известным признакам.
4. Связанные требования добавляются в трассировку процедуры, но не превращаются автоматически в отдельные пункты.
5. Нормативные требования, не покрытые контрольными процедурами, образуют список пробелов, а не тысячи автоматических пунктов.
6. ИИ обрабатывает только пробелы и неоднозначности: предлагает связь, формулировку нового пункта либо факт карточки вместе с цитатой из документа.
7. Итог сохраняет снимок карточки, решения классификатора, выбранные процедуры, нормативные связи и список неопределённостей.

## Первый рабочий инкремент

Первый инкремент переводит существующий шаблон из 235 пунктов в каталог контрольных процедур без потери строк. Применимость определяется по разделам классификатора:

- раздел 1 используется как базовый;
- разделы 2–7 включаются, когда в разделе есть хотя бы один применимый критерий;
- известные отрицательные признаки исключают неприменимые разделы;
- неизвестные признаки не блокируют остальные разделы и отображаются в пояснении результата.

Для Березниковского ЛПУМГ с подтверждёнными выбросами, водопользованием, отходами, ООПТ и водоохранной зоной, но без землепользования и недропользования, ожидается рабочий слой разделов 1, 2, 3, 4 и 7 — 179 референсных пунктов до нормативных дополнений.

Прямые элементы `requirements-registry-direct-v1` исключаются из итогового чек-листа. Сам реестр не удаляется и продолжает использоваться для трассировки, поиска, ответов по нормативной базе и анализа пробелов.

## Извлечение фактов из документов

Проиндексированные документы могут предлагать значения карточки: типы объектов, оборудование, разрешения, источники воздействия, зоны и иные признаки. Каждое предложение обязано содержать документ и точную цитату. Автоматическое извлечение не перезаписывает подтверждённые инспектором значения; пользователь принимает или отклоняет предложения отдельно.

Этот механизм реализуется после устойчивого перехода на каталог контрольных процедур, чтобы извлекаемые факты сразу использовались прозрачными правилами применимости.

## Роль ИИ

ИИ не определяет базовую применимость и не создаёт весь чек-лист заново. Он используется только для:

- предложения связей `unmapped`-процедур с реестром требований;
- анализа нормативных пробелов;
- формулирования нового проверочного вопроса по подтверждённому источнику;
- извлечения кандидатов фактов из документов.

Предложения ИИ не получают статус `verified` без детерминированной проверки или подтверждения инспектора.

## Ошибки и деградация

- Недоступность LLM не мешает сформировать референсный рабочий слой.
- Неполная карточка даёт частичный чек-лист и список неучтённых фактов.
- Отсутствие точной связи с реестром не удаляет утверждённую контрольную процедуру.
- Пункт без нормативного основания не может попасть в итоговый чек-лист.
- Каждый итоговый пункт содержит происхождение и объяснение применимости.

## Проверка результата

Инкремент считается завершённым, когда:

- все 235 пунктов исторического шаблона доступны в каталоге процедур;
- карточка Березниковского ЛПУМГ детерминированно выбирает 179 пунктов до дополнений;
- контрастная карточка с отсутствующими воздействиями получает только базовый раздел;
- прямые строки реестра не раздувают итоговый чек-лист;
- неизвестные значения не блокируют запуск;
- каждый пункт сохраняет основание, происхождение и применимые критерии;
- сборка, доменные тесты и локальный Docker-сценарий проходят без предупреждений и ошибок.

## Вне первого инкремента

- автоматическое утверждение предложенных ИИ связей;
- жёсткое ограничение количества пунктов;
- удаление или сокращение исходного реестра требований;
- автоматическое изменение подтверждённой карточки без участия инспектора.
