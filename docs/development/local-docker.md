# Локальный Docker-стенд

Стенд предназначен для разработки и полного прогона перед отправкой изменений в удалённый репозиторий. Он не подключается к базе хостинга и не использует PostgreSQL, уже работающий на локальном порту `5432`.

## Состав

- приложение: `http://127.0.0.1:18080`;
- PostgreSQL 17 с pgvector: `127.0.0.1:15432`;
- отдельный volume `ossdemo-db-data` для БД;
- отдельный volume `ossdemo-app-data` для моделей и поискового индекса.

## Первый запуск

Локальный `.env.local` создаётся из `.env.local.example` и не отслеживается Git. Для обычного запуска токен LLM не требуется.

```powershell
Copy-Item .env.local.example .env.local
./scripts/local-docker.ps1 Up
```

Первый запуск загружает локальные модели эмбеддингов и reranker размером более 1 ГБ, поэтому может занимать до 15 минут. Проверка ждёт готовность приложения, но немедленно завершается ошибкой, если контейнер остановился.

## Команды

```powershell
./scripts/local-docker.ps1 Status
./scripts/local-docker.ps1 Verify
./scripts/local-docker.ps1 Verify -RequireIndexedRag
./scripts/local-docker.ps1 Logs
./scripts/local-docker.ps1 Down
```

`Down` удаляет контейнеры и сеть, но сохраняет данные в volumes. Скрипт намеренно не содержит автоматического удаления volumes.

`Verify -RequireIndexedRag` дополнительно требует непустой индекс и выполняет диагностический гибридный поиск без обращения к LLM.

Проверка также контролирует структурированную карточку объекта и экран автоматизированного чек-листа: готовность карточки, сводку композиции, разрывы покрытия и трассировку пунктов.

## Автоматизированный чек-лист

Перед формированием откройте карточку объекта, задайте для всех обязательных признаков состояние `Есть` или `Нет`, сохраните и нажмите `Подтвердить карточку`. Состояние `Не установлено` намеренно блокирует итоговый чек-лист.

При создании запуска приложение сохраняет неизменяемый снимок:

- версию и статус подтверждения карточки;
- 49 решений классификатора с использованными фактами;
- выбранные требования и проверочные пункты;
- разрывы нормативного покрытия;
- SHA-256 файлов mapping, реестра требований и каталога пунктов.

Сформированный из утверждённого каталога запуск не обращается к LLM. После перезапуска контейнера снимок и идентификаторы выбранных пунктов восстанавливаются из PostgreSQL.

## Подключение LLM

Для проверки ИИ-консультанта добавьте `AI__ApiToken` только в `.env.local` и пересоздайте приложение:

```powershell
./scripts/local-docker.ps1 Up
```

Модель задаётся локальным параметром `AI__Model` (по умолчанию `qwen3_30b`). Реальная проверка консультанта выполняется только явно и расходует один запрос к LLM:

```powershell
./scripts/local-docker.ps1 Verify -RequireIndexedRag -RequireLlm
```

Проверка требует непустой grounded-ответ, имя модели и хотя бы один найденный источник, но не печатает токен или полный ответ в консоль.

Ответ считается grounded только после серверной проверки ссылок `[S1]`, `[S2]` и далее. Ссылка должна указывать на реально переданный модели источник; ответ без ссылок или со ссылкой за пределами списка заменяется безопасным сообщением без нормативного вывода. Это правило одинаково для обычного и потокового режимов.

Бесплатный эталонный прогон гибридного поиска по восьми нормативным сценариям:

```powershell
./scripts/evaluate-rag.ps1
```

Для выборочной оценки полного ответа модели используйте `-UseLlm -MaxCases N`. Такой запуск расходует по одному LLM-запросу на сценарий:

```powershell
./scripts/evaluate-rag.ps1 -UseLlm -MaxCases 2
```

Сценарии хранятся в `data/evals/rag-grounding-cases.json` и фиксируют ожидаемую тему источника и обязательную лексику ответа.

Не добавляйте `.env.local` в Git и не переносите в него строку подключения к БД хостинга.
