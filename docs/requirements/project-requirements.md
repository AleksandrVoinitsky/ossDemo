# АИ ООС Demo — требования к стенду по сценарию показа

Документ фиксирует требования к demo-стенду «Ассистент инспектора (инженера) по ООС» на основании файла `сценарий.txt`.

Главный приоритет текущего этапа — обеспечить уверенный демонстрационный проход по сценарию: от показа заранее подготовленных данных до генерации, верификации, утверждения и экспорта индивидуального чек-листа.

## 1. Источник и границы документа

### 1.1. Основной источник

- `сценарий.txt` — сценарий demo-показа.

### 1.2. Назначение документа

Документ нужен разработчикам и AI-агентам, которые продолжают проект. Он должен отвечать на вопросы:

- что именно должно быть показано на демо;
- какие экраны и действия нужны для каждого блока сценария;
- какие данные должны быть заранее подготовлены;
- какие функции обязательны для показа, а какие являются дополнительными;
- по каким критериям считать стенд готовым.

### 1.3. Граница Demo

Demo показывает полный пользовательский цикл подготовки чек-листа на заранее загруженных и подготовленных данных. Для показа допустимы управляемые mock-реализации, если интерфейс не вводит пользователя в заблуждение и демонстрирует ожидаемую бизнес-логику.

Промышленная отказоустойчивость, полноразмерный импорт всех типов документов, юридически значимое утверждение результатов проверки и интеграции с внешними корпоративными системами не входят в обязательный scope текущего demo-стенда.

## 2. Цель demo-показа

Показать, как система помогает инспектору ООС быстрее и прозрачнее подготовить индивидуальный чек-лист для плановой проверки.

Стенд должен продемонстрировать, что система:

- использует реальные предоставленные для демо данные;
- хранит единый классификатор критериев контроля;
- ведёт цифровые паспорта объектов проверки;
- использует базу знаний с нормативными документами;
- учитывает ОРД, нарушения за последние 5 лет и предыдущие чек-листы;
- формирует проект чек-листа;
- подсвечивает статусы пунктов;
- оставляет финальное решение за инспектором;
- позволяет подтвердить и экспортировать результат.

Ключевая ценность: сокращение времени подготовки чек-листа, повышение полноты, точности, прозрачности и стандартизации процесса.

## 3. Пользователь и роль

Основной пользователь demo-сценария — инспектор или инженер по охране окружающей среды.

Для demo достаточно одной роли с полным доступом к разделам:

- классификатор;
- объекты проверки;
- база знаний;
- реестр нарушений;
- шаблоны чек-листов;
- график проверок;
- новый чек-лист;
- результат чек-листа;
- AI-консультант;
- журнал действий, если он есть в интерфейсе.

## 4. Структура сценария показа

Сценарий состоит из пяти блоков:

1. Введение и контекст.
2. Подготовительный этап.
3. Основной процесс: генерация чек-листа.
4. Дополнительные сценарии.
5. Заключение.

Основной демонстрационный маршрут должен проходиться без ручного вмешательства разработчика и без необходимости менять данные во время показа.

## 5. Блок 1. Введение и контекст

### 5.1. Цель блока

Дать аудитории контекст: показывается прототип ассистента инспектора ООС, который помогает подготовить индивидуальный чек-лист для плановой проверки.

### 5.2. Что должно быть видно в интерфейсе

На главном экране или стартовой панели должны быть понятны:

- название системы: «АИ ООС» или «Ассистент инспектора ООС»;
- назначение: подготовка плановой проверки и индивидуального чек-листа;
- основной путь: готовые данные → выбор объекта → ОРД → шаблон → генерация → проверка → экспорт;
- быстрые переходы к ключевым разделам.

### 5.3. Требование к формулировке

Интерфейс и демонстрационный текст должны поддерживать тезис:

> Система работает с предоставленными для демо данными и показывает, как сокращается подготовка чек-листа.

## 6. Блок 2. Подготовительный этап

Подготовительный этап показывает данные, которые заранее загружены в систему и используются генерацией.

### 6.1. Классификатор критериев контроля

#### Экран

Раздел «Классификатор».

#### Что показать

- Иерархическое дерево или список разделов.
- Основные группы: атмосфера, вода, отходы и другие разделы ООС.
- Привязку требований к разделам классификатора.
- Пояснение, что классификатор задаёт структуру любого чек-листа.

#### Требования

- Классификатор должен быть отдельным справочником, а не обычным документом базы знаний.
- У разделов должны быть понятные названия и/или коды.
- Интерфейс должен показывать, что все требования и пункты чек-листа группируются по классификатору.

### 6.2. Объекты проверки

#### Экран

Раздел «Объекты проверки».

#### Что показать

- Список объектов.
- Выбор одного объекта для основного сценария.
- Цифровой паспорт объекта.
- Категорию НВОС.
- Функциональные зоны.
- Выбранные разделы классификатора.

#### Требования

- У основного demo-объекта профиль должен быть заполнен и готов к генерации.
- Должно быть видно, какие разделы проверки применимы к объекту.
- Желательно показать хотя бы один объект с неполным профилем, чтобы было понятно, что система умеет блокировать неподготовленные данные.

### 6.3. База знаний

#### Экран

Раздел «База знаний».

#### Что показать

- Список загруженных нормативных документов.
- Примеры источников: СТО, 7-ФЗ, 89-ФЗ и другие предоставленные документы.
- Статус индексации.
- Привязку документов или фрагментов к классификатору.

#### Требования

- Документы должны выглядеть заранее загруженными и проиндексированными.
- Для демонстрации нужны цитаты или ссылки на источники, которые затем появятся в чек-листе или ответе AI-консультанта.
- Если используется mock-режим, он должен выдавать заранее подготовленные ответы без случайного поведения.

### 6.4. Реестр нарушений

#### Экран

Раздел «Реестр нарушений».

#### Что показать

- Акты, предписания или нарушения за последние 5 лет.
- Привязку нарушений к объекту.
- Группировку по разделам классификатора.
- Примеры нарушений, которые влияют на статус пункта чек-листа.

#### Требования

- Повторяющееся нарушение должно приводить к статусу пункта `Контрольный`.
- Нарушение с неустранённым или просроченным сроком должно приводить к статусу `Критический`.

### 6.5. Шаблоны чек-листов

#### Экран

Раздел шаблонов или блок выбора шаблона в мастере чек-листа.

#### Что показать

- Наличие шаблонов двух уровней: Общества и филиала.
- Возможность выбрать шаблон уровня филиала для основного сценария.

#### Требования

- В основном сценарии должен быть доступен шаблон уровня филиала.
- Шаблон должен задавать табличную структуру результата.

## 7. Блок 3. Основной процесс: генерация чек-листа

Основной процесс — центральная часть demo. Он должен быть реализован как последовательный маршрут, понятный человеку, который впервые видит систему.

### 7.1. Шаг 1. Выбор объекта

#### Экран

Раздел «График проверок» или «Новый чек-лист».

#### Действие демонстратора

Открыть график проверок, выбрать запись проверки и нажать «Создать чек-лист» либо открыть мастер создания чек-листа напрямую.

#### Что система должна показать

- Запись в плане проверок.
- Объект проверки.
- Месяц или период проверки.
- Ответственного инспектора.
- Автоматически подставленный профиль объекта.

#### Требования

- Из графика должен быть понятный переход к созданию чек-листа.
- Основной объект должен быть готов к генерации.
- Система должна показать, что профиль объекта и ответственный подставлены автоматически.

### 7.2. Шаг 2. Загрузка ОРД

#### Экран

Раздел загрузки ОРД в мастере или отдельный раздел «ОРД».

#### Действие демонстратора

Показать загрузку или выбор заранее подготовленных организационно-распорядительных документов.

#### Что показать

- Кнопку «Загрузить ОРД».
- Выбор файлов PDF/DOCX или drag-and-drop.
- Список загруженных документов.
- Примеры документов: приказ, распоряжение, программа ПЭК.
- Извлечённые или имитированные требования, поручения, сроки и ответственных.

#### Требования

- Для demo достаточно заранее подготовленного набора документов.
- Должно быть видно, какие ОРД влияют на будущий чек-лист.
- Система должна показывать результат обработки: что найдено и какой пункт или раздел чек-листа будет затронут.

### 7.3. Шаг 3. Выбор шаблона

#### Экран

Мастер нового чек-листа.

#### Действие демонстратора

Выбрать шаблон уровня филиала.

#### Что показать

- Список доступных шаблонов.
- Шаблон уровня Общества.
- Шаблон уровня филиала.
- Выбранный шаблон для текущего чек-листа.

#### Требования

- Нельзя запускать генерацию без выбранного шаблона.
- Выбранный шаблон должен отображаться в результате чек-листа.

### 7.4. Шаг 4. Запуск генерации

#### Экран

Мастер нового чек-листа, этап генерации.

#### Действие демонстратора

Нажать кнопку «Сгенерировать».

#### Что система должна показать

- Прогресс-бар или сообщение «Идёт анализ...».
- Параллельную работу четырёх источников/агентов:
  - агент базы знаний ищет требования в законах и СТО;
  - агент ОРД извлекает требования из загруженных документов;
  - агент нарушений анализирует нарушения за последние 5 лет;
  - агент истории смотрит предыдущий чек-лист.
- Через несколько секунд — переход или ссылку на сгенерированный проект чек-листа.

#### Требования

- Генерация должна быть предсказуемой для demo-показа.
- Если используются mock-данные, этапы анализа всё равно должны визуально соответствовать четырём агентам из сценария.
- В результате должны появиться пункты из разных источников: база знаний, ОРД, нарушения, предыдущий чек-лист.

### 7.5. Шаг 5. Просмотр и верификация чек-листа

#### Экран

Интерактивный результат чек-листа.

#### Что показать

- Сформированный проект чек-листа.
- Структуру по разделам классификатора.
- Табличные колонки:
  - `№`;
  - `Наименование`;
  - `Основание`;
  - `Да/Нет/Не применяется`;
  - `Примечание`.
- Статусные пометки и ссылки на источники.

#### Статусы пунктов

| Цвет | Статус | Значение |
|---|---|---|
| Зелёный | Включён / обычный пункт | Пункт применим и включён в проверку |
| Синий | Контрольный | Нарушение повторялось за последние 5 лет или пункт перенесён из истории |
| Красный | Критический | Нарушение не устранено в срок |
| Жёлтый | Требует решения | Система не уверена или есть неоднозначность |

#### Требования

- Цвет не должен быть единственным носителем смысла: рядом должен быть текстовый статус.
- У каждого пункта должен быть источник или явная пометка, почему источник требует проверки.
- В demo-результате должен быть минимум один пункт каждого ключевого статуса: зелёный, синий, красный, жёлтый.

### 7.6. Шаг 6. Разрешение эскалаций

#### Экран

Интерактивный результат чек-листа.

#### Действие демонстратора

Открыть жёлтый пункт со статусом `Требует решения` и выбрать действие `Включить`.

#### Возможные действия инспектора

- `Включить` — пункт становится зелёным.
- `Исключить` — пункт удаляется или скрывается как исключённый.
- `Изменить формулировку` — пункт остаётся в чек-листе с ручной правкой.
- `Оставить как есть` — пункт остаётся жёлтым, а чек-лист не может перейти в статус `Готов`.

#### Требования

- Основной demo-путь должен показывать действие `Включить`.
- После выбора `Включить` статус и цвет пункта должны измениться.
- Решение инспектора должно быть видно в интерфейсе и желательно фиксироваться в журнале.
- Чек-лист нельзя подтвердить, если остались неразрешённые жёлтые пункты.

### 7.7. Шаг 7. Ручное добавление требования

Шаг опционален, но желателен для полного показа возможностей инспектора.

#### Экран

Интерактивный результат чек-листа.

#### Действие демонстратора

Нажать «Добавить пункт», ввести текст, выбрать раздел классификатора и сохранить.

#### Требования

- Пользователь должен иметь возможность добавить пункт вручную.
- При добавлении нужно выбрать раздел классификатора.
- Система должна заявлять или выполнять проверку на дубли.
- Ручной пункт должен иметь визуальную пометку или понятный источник `Добавлено инспектором`.

### 7.8. Шаг 8. Утверждение и экспорт

#### Экран

Интерактивный результат чек-листа.

#### Действие демонстратора

Нажать «Подтвердить чек-лист», показать сообщение об успехе и кнопки скачивания.

#### Что показать

- Проверку отсутствия неразрешённых жёлтых пунктов.
- Перевод чек-листа в статус `Готов`.
- Сообщение об успешном подтверждении.
- Кнопки скачивания: PDF, DOCX, XLSX.
- Открытие XLSX-файла как наиболее удобного формата для анализа и фильтрации.

#### Требования

- Экспорт должен быть доступен минимум в PDF, DOCX и XLSX в рамках demo-сценария.
- XLSX должен содержать понятную табличную структуру чек-листа.
- Если реальные файлы ещё не генерируются, для demo должны быть подготовлены стабильные файлы-заглушки, которые можно скачать и открыть.

## 8. Блок 4. Дополнительные сценарии

Дополнительные сценарии показываются только при наличии времени. Они не должны блокировать основной happy path.

### 8.1. Диалоговый режим

#### Что показать

- Инспектор задаёт вопрос по чек-листу, например: «Почему этот пункт считается критическим?».
- Система отвечает с цитатой из документа.

#### Требования

- Ответ должен ссылаться на источник.
- Если источник не найден, система должна честно сообщить об отсутствии релевантных данных.
- Для demo допустим mock-ответ, если он стабилен и содержит цитату/источник.

### 8.2. Управление статусами чек-листа

#### Что показать

- Переход чек-листа в статус `Архивирован` после проверки.
- Использование архивного чек-листа как предыдущего для следующих генераций.

#### Требования

- Статусная модель должна включать минимум: `В работе`, `Готов`, `Архивирован`.
- Предыдущий чек-лист должен быть виден как источник для агента истории.

### 8.3. Просмотр реестра нарушений

#### Что показать

- Нарушения из актов автоматически или демонстрационно привязаны к объекту.
- Нарушения группируются по разделам классификатора.
- Из нарушений формируются контрольные и критические пункты.

## 9. Блок 5. Заключение

В финале demo должно быть понятно, что система:

- автоматически собирает требования из законов, ОРД, нарушений и истории;
- структурирует требования по единому классификатору;
- предоставляет инспектору готовый проект чек-листа;
- выделяет сомнительные пункты для решения инспектора;
- помогает сократить время подготовки;
- повышает полноту, точность, прозрачность и стандартизированность процесса.

## 10. Обязательные экраны demo-стенда

Для прохождения сценария нужны следующие экраны или функционально эквивалентные блоки:

|---|---:|---|
| Главная | да | Вводный контекст и быстрые переходы |
| Классификатор | да | Показ структуры критериев контроля |
| Объекты проверки | да | Показ цифрового паспорта объекта |
| База знаний | да | Показ нормативных источников и индексации |
| Реестр нарушений | да | Показ нарушений за последние 5 лет |
| Шаблоны | да, отдельным экраном или внутри мастера | Выбор уровня Общества/филиала |
| График проверок | да | Старт создания чек-листа из плана |

## 11. Минимальные demo-данные

Для стабильного показа должны быть заранее подготовлены:

- один основной объект с полностью заполненным цифровым паспортом;
- несколько дополнительных объектов для справочника;
- активный классификатор с разделами по ООС;
- база знаний с документами СТО, 7-ФЗ, 89-ФЗ и другими источниками из demo-набора;
- 1–2 ОРД для загрузки или выбора: приказ, распоряжение, программа ПЭК;
- нарушения за последние 5 лет;
- предыдущий чек-лист для агента истории;
- шаблон уровня Общества;
- шаблон уровня филиала;
- готовый результат генерации с разными статусами пунктов;
- экспортные файлы PDF, DOCX и XLSX или генератор этих файлов;
- один подготовленный вопрос для AI-консультанта с цитатой из источника.

## 12. Логика генерации для demo

Сценарий говорит о запуске четырёх агентов. В рамках demo это должно быть представлено как видимый процесс анализа четырёх источников:

1. База знаний — законы, СТО и нормативные документы.
2. ОРД — загруженные приказы, распоряжения, программы и планы.
3. Реестр нарушений — нарушения за последние 5 лет.
4. История — предыдущий чек-лист.

Результат генерации должен объединять пункты из этих источников и показывать причину включения.

Для текущего demo допустимы два режима:

- `Mock` — заранее подготовленный результат с имитацией работы агентов;
- `Integrated` — реальная обработка через подключённые сервисы.

Какой бы режим ни использовался, поведение на показе должно быть стабильным и повторяемым.

## 13. Статусы чек-листа и пунктов

### 13.1. Статусы чек-листа

| Статус | Значение | Правило перехода |
|---|---|---|
| В работе | Чек-лист сформирован и проверяется инспектором | После генерации |
| Готов | Инспектор подтвердил чек-лист | Только если нет жёлтых пунктов `Требует решения` |
| Архивирован | Чек-лист завершён и используется как история | После проверки, дополнительный сценарий |

### 13.2. Статусы пунктов

| Статус | Цвет | Источник статуса |
|---|---|---|
| Включён | зелёный | Обычный применимый пункт из БЗ, ОРД, истории или ручного решения инспектора |
| Контрольный | синий | Повторяющееся нарушение за последние 5 лет или перенос из предыдущего чек-листа |
| Критический | красный | Нарушение не устранено в срок |
| Требует решения | жёлтый | Неоднозначность, низкая уверенность, противоречие или ручная проверка применимости |

## 14. Экспорт

Demo-сценарий требует показать скачивание и открытие результата.

Обязательные форматы:

- PDF;
- DOCX;
- XLSX.

Для XLSX обязательно показать структуру, удобную для анализа и фильтрации. Минимальные колонки:

- `№`;
- `Наименование`;
- `Основание`;
- `Да/Нет/Не применяется`;
- `Примечание`.

Дополнительно можно включить служебные колонки:

- раздел классификатора;
- статус;
- источник;
- причина включения.

## 16. Негативные проверки, которые не должны ломать demo

Основной показ должен идти по happy path, но система должна иметь понятное поведение в базовых отклонениях:

| Ситуация | Ожидаемое поведение |
|---|---|
| Не выбран объект | Нельзя запустить генерацию, показать понятное сообщение |
| Профиль объекта неполный | Блокировать генерацию или показать статус `Требует доработки` |
| Не загружены/не выбраны ОРД | Разрешить demo на подготовленных данных или явно показать предупреждение |
| Не выбран шаблон | Нельзя запустить генерацию |
| Остались жёлтые пункты | Нельзя перевести чек-лист в статус `Готов` |
| Ошибка экспорта | Показать понятное сообщение и возможность повторить |
| AI-источник не найден | Сообщить, что релевантных данных нет, не выдумывать ответ |

## 18. Критерии готовности demo

Стенд готов к показу по `сценарий.txt`, если:

- приложение открывается локально или по согласованному адресу;
- стартовый экран объясняет назначение ассистента инспектора ООС;
- можно последовательно показать классификатор, объекты, базу знаний, нарушения и шаблоны;
- из графика или мастера можно начать создание чек-листа;
- выбранный объект имеет заполненный профиль;
- можно показать загрузку или выбор ОРД;
- можно выбрать шаблон уровня филиала;
- кнопка «Сгенерировать» запускает видимый процесс анализа;
- процесс анализа показывает четыре источника/агента: БЗ, ОРД, нарушения, история;
- результат чек-листа открывается после генерации;
- в результате есть таблица с колонками из сценария;
- пункты имеют зелёный, синий, красный и жёлтый статусы;
- жёлтый пункт можно включить и увидеть изменение статуса;
- можно показать ручное добавление требования;
- чек-лист можно подтвердить после разрешения жёлтых пунктов;
- доступны PDF, DOCX и XLSX;
- XLSX можно открыть и показать структуру;
- при наличии времени можно показать AI-вопрос с цитатой;
- финальный рассказ подтверждает ценность: быстрее, полнее, прозрачнее, стандартизированнее.
