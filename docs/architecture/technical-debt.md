# Технический долг и следующие этапы

Документ фиксирует обнаруженные проблемы, которые не следует смешивать с безопасной реорганизацией файлов. Приоритеты определены по влиянию на последующую разработку.

## Выполняется в текущей ветке

- отделение исходного кода от базы знаний, seed-данных и локальных материалов;
- удаление `.env` из Git tracking;
- единые правила каталогов, сборки и проверки;
- сохранение существующих publish-путей и автодеплоя.

## Этап 1 — границы web-приложения

`src/OssDemo.Web/Program.cs` содержит регистрацию DI, middleware и большое количество endpoint-обработчиков. Следующее архитектурное изменение должно переносить API по функциональным областям в отдельные extension-классы, сохраняя URL и DTO:

1. RAG и диагностика;
2. база знаний;
3. operational dashboard и объекты;
4. расписание;
5. запуск и остановка приложения.

Критерий завершения: `Program.cs` отвечает только за композицию приложения, а каждый модуль API тестируется отдельно.

## Этап 2 — стили и клиентский код

`wwwroot/css/site.css` содержит около 96 КБ стилей разных экранов. Следует выделить базовые tokens/layout и стили функциональных областей, не меняя визуальный результат. JavaScript уже в основном разделён по страницам; для него сначала нужны lint/format-настройки и только затем рефакторинг общих функций.

Критерий завершения: изменение одного экрана не требует просмотра единого монолитного stylesheet, а сборка формирует один предсказуемый комплект ресурсов.

## Этап 3 — тестовая инфраструктура

Оба набора проверок сейчас являются консольными приложениями. Это быстро, но затрудняет фильтрацию, отчёты CI и точную локализацию падений. Рекомендуется постепенно перевести их на стандартный test SDK (xUnit или NUnit), сохраняя текущие проверки как исходные контракты.

Критерий завершения: `dotnet test OssDemo.slnx --configuration Release` запускает все тесты и выдаёт машиночитаемый результат.

## Этап 4 — воспроизводимость frontend-зависимостей

В `wwwroot/lib/` хранятся полные vendor-наборы Bootstrap, Bootswatch, jQuery и FullCalendar, включая source maps и неминифицированные варианты. Нужно выбрать один управляемый способ поставки (LibMan или npm build) и оставить в publish только используемые файлы. Это отдельная миграция, потому что она влияет на Docker-сборку и клиентский кэш.

## Этап 5 — CI перед автодеплоем

После стандартизации тестов добавить обязательную проверку restore/build/test/publish для pull request. Автодеплой должен получать только прошедший эти проверки commit. Секрет-сканирование следует включить до следующей ротации production-ключей.

## Не делать попутно

- не дробить один web-проект на несколько assemblies без измеримой необходимости;
- не менять схему PostgreSQL ради структуры каталогов;
- не подключать `data/import/` к runtime автоматически;
- не заменять RAG-библиотеки и модели в рамках организационных изменений;
- не удалять локальные исходные материалы до подтверждения их резервного хранения.
